# 历史会话证据补充：下一轮质量、耗时与 token 成本优化

- 日期：2026-09-26
- 定位：对“下一轮演进方向”的**独立实证补充**，不替换原建议，不直接授权生产策略变更。
- 代码参照：`9c0f8c743f`。本次历史事件均早于这次修复，**不能用于证明修复后的效果**。
- 数据附件：[脱敏统计与输入指纹](./2026-09-26-session-history-optimization-evidence.json)。下文会话编号均为相对路径 SHA-256 的前 16 位，不包含原始会话正文。
- 执行方式：本机离线扫描、规则统计、定向人工核查；未调用分类模型、未上传会话、未修改产品实现或原有分析脚本。

## 1. 结论：先降低失败等待与主会话的大上下文成本

历史证据支持的优先顺序是：

1. **P0：凭据/路由不可用时的早期失败与有界恢复。** 不把配置性失败当成无限可重试的瞬时错误；尤其避免多个子代理重复消耗同一条已不可用路线。
2. **P0：先补任务验收口径，不宣称现阶段能算“每个成功任务的成本”。** 同时观察现有交接是否真正使用，而不是默认继续增加 handoff 字段。
3. **P1：针对高费用主会话做上下文与阶段交接实验。** 成本集中在少数会话及大上下文请求；不是先全局换便宜模型或强制所有任务在 200k 压缩。
4. **P1：消除确定的读取交互错误，优先分页继续读与工具契约提示。** 有明确的“想读下一页，实际又拿到第一页”样本；不要把所有同路径重读都拦掉。
5. **P1：将 thinking-loop / 流式中断做成可回放的失败案例。** 保护已经完成的工作，校准既有恢复边界；不能为省时间关闭循环检测或降低验收要求。

**暂不优先：** 全局增加并发、全面降低 effort、扩建 handoff schema、统一缩短输出、增加固定协调代理。当前样本无法证明这些动作有净收益。

这些是按证据强度、近期性和影响范围排序的实验方向，**不是收益百分比承诺**。

## 2. 样本范围与可信度

### 2.1 选择方法

使用现有 `scripts/session-stats/audit.ts`：

```sh
bun scripts/session-stats/audit.ts \
  --since 30d --folder tencent --no-llm --json <本机私有输出文件>
```

该脚本按“主会话及其子目录的最大文件 mtime”选择**整个会话组**，不是逐事件的最近 30 天过滤。

- 既有审计返回 352 个有统计结果的会话组；排除当前评审/研究会话及其全部子代理后，分析 **351 个主会话、902 个子会话，共 1,253 个 JSONL 文件**。
- 涉及 33 个项目目录；其中 oh-my-pi 为 151 个主会话、366 个子会话，其余为其他项目。
- 不纳入 `-tmp-*` 测试/benchmark 目录。因此没有把本地 mock benchmark 当成真实使用记录。
- 采集时间：`2026-09-26T08:26:21.610Z`；选中记录的事件跨度为 `2026-08-22T15:50:31.022Z` 至 `2026-09-25T16:00:42.258Z`。较早事件来自最近仍活跃的长会话。
- 另按事件时间分析 `2026-09-19T00:00:00Z` 之后的记录，区分近期仍存在的问题与旧版本事件。
- 解析错误 0；每份文件读取前后检查 size/mtime，记录内容 SHA-256。没有复制原始正文到仓库。
- 输入清单指纹：`1cabbcb9548fd4c50ec71ac8b160d84a0f05c3ad151c534e924ae766c672ea35`。

### 2.2 指标能说明什么

| 指标 | 口径与限制 |
|---|---|
| 请求数 | 持久化 assistant 消息记录数；不保证等于所有实际 HTTP 请求数，也未消除跨文件复制历史的可能重复 |
| token | 消息中已有 usage；不是重新分词；不把不同 provider 的缓存口径自动视为完全等价 |
| 费用 | 累加历史 `usage.cost.total` 的**名义费用**，不是账单；失败记录大量为 0，不能认定失败没有实际成本 |
| 工具输出量 | `ceil(返回文本字符数 / 4)` 的估算，只用于比较流量；不是 provider 精确 token 或可节省费用 |
| 请求延迟 | 有记录的 TTFT / generation；不能累加并行请求来声称端到端可节省时间 |
| 重复读取 | 同文件内、同归一化资源、相同返回文本摘要、没有观察到变更边界的候选；仍无法证明目的相同或外部状态未变 |
| 验收结果 | 只接受显式父级最终验收记录；进程退出、工具无错误、子代理 completed 均不代替任务验收 |

## 3. 当前不可计算项：这是评估前置条件，不是优化结果

现有 `subagent-report.ts` 的解析器对同一批记录给出：

| 项目 | 已知 / 未知 |
|---|---:|
| 父子文件关联 | 902 / 0 |
| assistant 模型字段 | 68,459 / 0 |
| TTFT / generation | 65,729 / 2,730 |
| task 成员 completionKind | 616 / 139（共 755 个成员观察） |
| spawnQueueMs | 96 / 659 |
| requestPhaseQueueMs | 0 / 755 |
| 父级最终验收 | **0 / 351** |

- `e2eMs`、通过验收的任务单位成本、首次通过率、质量保持率目前均**不可从该样本可靠计算**。
- 755 个 task 成员观察不等于 902 个子文件；其他派生/顾问/恢复通道不能强行塞进同一分母。
- 已知 completionKind 为 completed 473、timeout 29、hard_abort 114，另有 unknown 139。`hard_abort` 可能是用户主动取消，不应全算产品失败；completed 也不代表任务验收通过。
- 选中项目历史中未检测到显式 workflow 调用/收据标记。workflow 样本需另外从专用运行记录收集，不能与这批交互会话拼出一个“全平台成功率”。
- 490 次直接 task 调用里未观察到 `context` 内的 `evidence-handoff` 围栏，用户消息文本中也未观察到该围栏。**这不等于没有自由文本交接，也不能证明新实现没有接通**：本样本早于刚提交的修复。

因此，原建议中的“全部尝试费用 ÷ 验收通过任务数”应当被保留为**未来指标**，不是现成统计。先让新版本真实产生、消费并关联验收/交接证据，再考虑扩展字段。

## 4. 最高价值候选与一手证据

### H1 · P0：对凭据/路由不可用的重复请求做早期止损

全样本有 **1,234 条 assistant error 记录**。定向读取实际 `errorMessage` 后归类：

| 类别 | 主会话 | 子会话 | 时间意义 |
|---|---:|---:|---|
| 限流 / 冷却 | 75 | 386 | 461 条全部发生于 8 月 30 日至 9 月 6 日；不能据此宣称当前仍有同等规模限流问题 |
| 凭据 / 路由不可用 | 84 | 275 | 359 条，覆盖 48 个主会话组，最近到 9 月 21 日 |
| thinking-loop | 27 | 127 | 154 条，覆盖 49 个主会话组，最近到 9 月 25 日 |
| 传输 / 流中断 | 28 | 45 | 73 条，最近到 9 月 25 日 |
| provider 服务错误 | 32 | 53 | 85 条 |
| 其他 / 取消 | 50 | 52 | 不把未归因错误伪装成同一种根因 |

近期事件窗口中有 7,197 条 assistant 消息、63 条 assistant error；其中 **48 条是凭据/路由不可用**，分布于 15 个主会话组；限流/冷却为 0。

**核查案例 E1：** `54004ad2dae12e59` 的第 264–274 条 JSONL 记录，连续 11 次出现 API-key 校验失败；中间没有用户消息或成功 assistant 消息。首尾为 `2026-09-21T08:56:58.366Z` 和 `09:10:34.580Z`，跨度 **13.60 分钟**。这证明重复失败与等待的存在，但不是可直接相减的端到端节省值；期间也可能包含上游内部恢复与退避。

**推荐动作：**

- 先回放上述错误，核对 gateway/provider 的错误分类与现有 retry/fallback 处理。
- 区分需配置修正的失败、短期冷却与传输瞬时失败；未知故障保持保守，不靠错误字符串猜测账户权限。
- 在现有可用性预检、重试/回退和健康状态 owner 上修正边界，保留用户可见的失败原因和已有产物。
- 跨 sibling 的已知不可用状态是否共享，需验证当前接线；不另建调度器。

已有 `src/latency/provider-health-breaker.ts` 是 workflow/profile 作用域的可选机制，不能直接当成普通会话全覆盖，也不应未经验证全局打开。

**验收：** 凭据明确不可用时不会继续相同的无效请求链；短暂故障恢复后仍能继续；无凭据泄漏、无误封正常路线。恢复正确性先过门，再比较失败链长度与等待跨度。

### H2 · P1：主会话大上下文与阶段性交接，比一刀切压缩子代理更值得先试

| 已记录资源 | 主会话 | 子会话 |
|---|---:|---:|
| assistant 消息 | 30,980 | 37,479 |
| 输入 token | 195,541,778 | 185,394,051 |
| 输出 token | 19,532,387 | 24,052,204 |
| cacheRead token | 4,311,425,438 | 2,884,051,465 |
| 名义费用 | 4,743.68 | 1,671.17 |

总名义费用约 **6,414.85**；主会话占 **73.95%**，尽管子会话占消息数 **54.75%**。模型分布和任务难度不同，不能把这个比例解释成父级效率低或子代理更划算。

更具实验价值的集中度：

- 前 10 个会话组占名义费用 **39.38%**，前 20 个占 **53.91%**。
- 主会话里 7,059 条请求的已记录上下文超过 200k，占主请求 **22.79%**，占主名义费用 **48.45%**。
- 近期窗口中对应比例仍为 **25.29% 的主请求、51.23% 的主费用**，不是只由旧会话造成。
- read + grep 占工具返回文本估算量 **86.75%**。这是上下文来源候选，不证明这些证据没有必要。

**推荐动作：** 固定 200k 仅作为分析分层点，选高费用会话回放，测试现有维护/交接机制能否在自然任务阶段边界保留未决约束、改动范围和验收证据，同时减少后续携带的内容。对照未改变模型、工具集、任务难度的同一任务。

不要默认拆分每个长会话：长任务可能确实需要这些证据。也不要先加“必须少读”规则或把所有模型窗口压成同一上限。

**验收：** 后续请求的上下文量与总完成成本下降，同时约束保留、恢复正确性、最终验收不下降。没有验收标签时只报告流量变化，不报告完成效率提升。

### H3 · P1：分页继续读的确定性错误，值得小步修；全局重读拦截证据不足

全样本 read 调用 56,999 次，成功返回 55,627 次；同资源再次读取候选 31,335 次。但进一步分解：

- 10,656 次中间有已观察到的变更/不透明操作边界，状态未知。
- 20,156 次返回不同视图或无法判定相同。
- 仅 **523 次**满足严格的“同返回文本、无已观察到变更边界”候选条件，占成功 read **0.94%**。
- 这些候选返回文本约 **255,277 估算 token**，约为所有 read 返回文本估算量的 **0.54%**；不是输入费用节省上限，也不是已证明浪费。
- 近期窗口为 22 个候选，约 12,743 估算 token。

**不能沿用“同路径重读很多，所以强制去重收益很高”的推理。** 不同范围、复核用途、外部修改和上下文恢复都可能合理。

定向抽查最大候选，发现两个具体、可回放的交互问题：

- **E2：** 子会话 `37eaa48f311f899f` 调用记录 15、24；第二次意图是“读取剩余 diff”，参数仍是相同 `artifact://262:raw`。两次返回都为 340 行中的前 300 行，页尾均提示从 `:301` 继续。另一子会话 `48487a81c52fb59f` 的记录 20、29 有同样行为。这里应修的是“继续读的定位”，不是禁止 reviewer 独立读原始证据。
- **E3：** `c13a8498dd06706e` 调用记录 36、39，把独立 `offset` 从 1 改成 301，却保持同一个 `:raw` path。两次实际返回都仍是 1,808 行中的前 300 行。全样本带旧 `offset/limit` 参数的 read 仅 21 次、近期 1 次，因此不能夸大成主成本来源。
- **反例 E4：** `a4381212eac40cb0` 调用记录 37、118，第二次明确是重新核查样式溢出。字节相同，不足以判为无意义重复。

**推荐动作：** 优先验证完整可执行的下一页 locator、参数不受支持时的明确反馈，以及当前工具契约的可发现性。复用现有 read 和恢复路径，不新增工具或强制停止规则。普通代码查找可对比 LSP/code-intel 的定点定位，但必须先证明减少了恢复往返。

**验收：** 真正拿到下一页/目标声明；不同视图、变更后重读和必要复核仍可执行；总工具往返与输入量联合下降。

### H4 · P1：循环与流中断的恢复保真

thinking-loop 154 条中有近期 8 条；传输/流中断 73 条中有近期 5 条。循环错误常没有 duration，且名义 usage 记录为 0，当前无法可靠量化其算力或费用。

建议选择错误前已有工具执行/修改的真实案例，回放既有恢复链，验证：

- 已成功执行的写入不会因为流重试而被重复执行。
- 保存的输出、未完成工具调用和当前约束仍可恢复。
- 同一类故障超过现有恢复边界时有明确结论，不靠重建全部上下文继续试。

这是恢复质量工作，不是关闭循环检测、盲目缩短 hard cap 或搭第二套“反循环系统”。

### H5 · P0 前置：验证/交接的使用率与有效性，而不是继续扩展字段

全样本没有最终验收回执，也没有观测到结构化 evidence-handoff 围栏。由此能得出的结论是**新机制的实际使用与收益尚不可测**，不是需要更复杂的 schema。

对新版本的小规模真实样本，先分别记录：

1. 普通会话与 workflow 的显式验收覆盖。
2. handoff 是否生成、是否被消费、是否因过期而拒绝。
3. 父级是否仍需重读相同证据，以及重读是否必要。
4. 有真实 terminal 结果的验证调用，而非仅有 async.running 确认。

本次启发式找到 15 对相同检查命令候选；逐项核查后有 5 对两次都只是 `async.running`。因此**不把这 15 对标成重复成功验证，不由此推算可以省掉多少全仓检查**。其余记录也缺少足够工作区身份来证明复用安全。

## 5. 对前一版建议的修正，而非重写

| 原建议 | 历史证据后的调整 |
|---|---|
| 正确完成一个任务的单位成本 | 保留为目标；先列不可计算项，补显式验收，不用 351 个未知结果做分母 |
| 强化子任务交付证据 | 先验证上一轮已经实现的交接是否使用、是否减少父级重读；不默认再加字段 |
| 验证分层与复用 | 保留安全价值；收益需补 workspace/terminal 证据，不能用简单命令重复数证明 |
| 读取/缓存优化 | 主会话大上下文先实验；全局重读拦截降级为小范围分页/定位交互修正 |
| 模型/effort 校准 | 延后；当前模型、时间与任务强度混杂，无质量标签不能排模型性价比 |
| 并发调参 | 延后；近期未见限流重现且 provider queue 无覆盖，不能直接扩大并发 |
| 新增优先项 | 凭据/路由失败链，以及循环/中断后的恢复保真 |

建议同等规模的新一轮按 H5 的最小观测前置、H1 的真实失败回放、H2 的单因素实验推进；H3 是有具体案例的小修，H4 用有状态失败场景验证。任务切片按真实代码 owner 拆分，不为凑并行创建额外协调层。

## 6. 证据与复现边界

### 已复用的实现

- `scripts/session-stats/audit.ts`：只执行 `--no-llm`；按实际 usage 分主/子会话，工具文本为字符数估算。
- `packages/coding-agent/src/latency/subagent-report.ts`：复用 JSONL 解析、父子关联、completionKind、队列与最终验收覆盖；未修改代码。
- `scripts/session-stats/subagent-thrash.py`：只读参考其状态未知边界与“候选不等于浪费”的方法；未执行、未改动该原有未跟踪文件，也不继承其预设 go/no-go 结论。
- 临时研究脚本位于本次会话的 `local/history-supplement-analysis.ts`，不进入产品源码；原始审计与路径映射仅作为本机临时中间结果，生成脱敏附件后删除，不进入仓库。

### 核查办法

附件保存每个源文件的脱敏 id、内容 SHA-256、字节数、mtime，以及整体清单指纹。id 生成规则为：`sha256(相对于 ~/.omp/agent/sessions 的路径).slice(0, 16)`；按本机路径计算即可定位本文案例，再按记录行号核查。

以后重跑 `--since 30d` 会选到不同样本，不能要求数值相同；若原始会话追加、清理或迁移，先核对内容指纹再比较。当前会话已整体排除，避免研究过程反过来抬高读取、子代理和费用统计。

### 不作出的结论

- 不把历史名义费用当成真实账单或成功任务成本。
- 不声称某模型更便宜就更适合实现/评审。
- 不声称历史优化机制尚未生成的收据证明当前生产代码断路。
- 不把长上下文、高耗时、重复读或中止本身标为质量失败。
- 不从请求时长相加、费用集中度或字节重复量直接导出节省比例。
- 不以本研究授权生产默认值变更、模型实网 A/B 或额外提示词规则。
